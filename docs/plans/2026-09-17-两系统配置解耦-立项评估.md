# 两系统配置解耦 — 立项评估（WP-H-4）

> 来源：《2026-09-10-协议收口与遗留债-解决计划》§9 WP-H 步骤 4。
> 性质：**只评估，不改配置、不改代码**。本文为立项裁决提供事实与代价口径。
> **状态（2026-09-18）：已按方案 B 实施完成**，见 §6 实施记录。本文档正文保留评估时事实，两处事实勘误见 §1 表内标注。

## 0. 结论速览

- **建议立项，方案 B（liu2 独立配置文件）**：双方加载器均已支持路径参数化，迁移 ≈ 拆文件 + 补 liu2 启动脚本，core/协议零改动，可即时回滚。
- **最强耦合不在"段"，而在 `llm` 段的"配置同源"**（2026-09-18 键级复核修正初版判断）：`llm` 共 12 键，**11 键两系统同读**（含 `main_api_key` / `consolidation_api_key`），即**改一处同时改变两个系统的 provider/model/密钥**；`storage` 段为"半共享"（3 键中 `sqlite_path` 同读）。另有一处真实隐患：`storage.sqlite_path` 原值 `data/sessions.db` **指向老系统会话库**，虽属 liu2 的休眠兜底（正常由 Rust 存储代理接管），一旦代理缺位即写入老系统数据 —— 这两点是本次解耦的实质收益。

**由此得出的两个关键结论**

1. **解耦前最实质的耦合是 `llm` 段的"配置同源"**：provider / model / API Key / base_url 两系统完全共用一份值（12 键中 11 键同读），**改一处即同时影响两个系统**。这不是"各读不同键子集"的弱耦合，而是全量共享。解耦后二者方可各自独立配置——这是方案 B 的主要收益。
2. **`storage` 段是"半共享"**：`sqlite_path` 两侧同读（liu2 兜底原指向老系统库，已在 §6 修正为 `data2/sessions.db`）；`session_ttl_days` / `cleanup_interval_hours` 属老系统专属，liu2 **尚未实现** TTL / 清理（与 P3 缺口"SessionStore TTL（外壳责任）"一致）。

## 2. 耦合风险清单

> **风险处置状态（2026-09-18 实施后回填）**：1–5 已由本次解耦**全部消解或显著缓解**；6–7 为解耦后**新增**的风险，须持续登记。解除方式见各条末尾。

1. **配置同源（原表述有误，已修正）**：`llm` 段并非"各读不同键子集"——实测 12 键中 **11 键两系统同读**（provider / model / **API Key** / base_url / max_context_tokens / consolidation_* / 两个超时键），**改一处即同时改变两个系统的行为**；`storage.sqlite_path` 亦两侧同读。这是最强耦合形态，而非弱耦合。→ **已消解**：两系统各持独立文件（§6），键值可独立演化。
2. **`${VAR}` 解析双实现**：同一文件被两套解析器各自展开，语义漂移风险（如默认值/嵌套展开规则不一致时难排查）。→ **已消解**（就配置文件而言）：各文件只被一套解析器读取；但**根 `.env` 仍共用**，两套 `load_dotenv(override=True)` 并存（见风险 7）。
3. **密钥泄露面扩大**：liu2 的 `main_api_key`/`consolidation_api_key` 与老系统密钥同文件，无法按系统做最小权限的备份/分发。→ **已缓解**：配置文件层面已分离（可各自备份/分发），但 `.env` 仍为两系统共用同一份密钥（一项独立决定，未在本次变更范围）。
4. **冻结隐性约束**：老系统已冻结却共同持有该文件；liu2 后续配置演进会被"共用文件"约束。→ **已消解**：liu2 配置演进不再触碰老系统文件。
5. **部署耦合**：无法只部署/回滚 liu2 的配置。→ **已消解**：删 `config-liu2.yaml` 即回滚（§6 回滚方式），不影响老系统。
6. **【新增】非 `core` 段无未知键校验 → typo 静默失效**：未知键拒绝**仅覆盖 `core` 段**（`CONFIG_UNKNOWN_KEY` 只用于 core）；`llm` / `storage` / `host_components` 段的键名写错会被**静默忽略**并回落默认值（实证：`llm.actvity_timeout=99` 不报错、直接回落 60/300；伪造顶层段名亦不报错）。解耦后两份 config 并存、键名靠复制粘贴，漂移更难察觉 —— 此风险因解耦而**放大**。→ **已立项评估（2026-09-18）**：见 `docs/plans/2026-09-18-配置校验严格性-立项评估.md`。结论：core-only 边界**原则合理且有契约依据**（`config.spec` §1 + 行为条款 C-1 + 套件 case 21 锚定），但落地有 3 个缺口 —— 其中 `host_components[].backend` 键名拼错会**静默回落内置 SQLite**，属**契约违规**（spec §3 明文"必填""不静默降级、不回落内置实现"），该修复零迁移成本。
7. **【新增】`.env` 的 `override=True` 会覆盖 `TEAGE2_CONFIG`**：liu2 在 `core/config.py:37` 以 `load_dotenv(override=True)` 模块级加载 `.env`，而 `create_app` 随后经 `os.getenv("TEAGE2_CONFIG")` 取配置路径 —— 若把 `TEAGE2_CONFIG` 写进 `.env`，将**覆盖** `start_liu2.ps1` 设置的值，静默切到别的配置文件（当前 `.env` 无该键，属潜在坑）。→ **已登记防御约定**：`TEAGE2_CONFIG` 只由启动脚本/命令行/进程环境设置，**禁止写入 `.env`**（见 §6 与 `CODEBUDDY.md`）。

## 4. 迁移代价评估（方案 B）

- **liu2 侧近似零代码改动**（评估口径；**实施勘误见下**）：`create_app(config_path=...)` 参数已存在；`load_config` 相对路径解析逻辑不变（新文件仍放仓库根或 `data2/`）。
  - **实施勘误（2026-09-18）**：仅"参数已存在"不足以完成解耦 —— uvicorn 以 `--factory` 调用 `create_app()` 不传参，故**必须补一处接线**才能让 liu2 读到新文件。实做：`create_app` 增 `os.getenv("TEAGE2_CONFIG")` 回落（`server/app.py:134-136`），属向后兼容的小改动，非"零改动"。
- 需要动的只有三处：
  1. 新建 `config-liu2.yaml`（从根 config.yaml 摘 4 段 + `${VAR}` 占位保留，`.env` 单一源不变）；
  2. 补一个 `start_liu2.ps1`（顺带解决"liu2 无启动脚本"问题）。**实施差异（2026-09-18）**：评估时设想"日志落 `d:/tmp`"，实做为**前台运行不自建重定向**（与老系统 `start.ps1` 一致，Ctrl+C 退出；重定向交由使用者按需处理），故未采用 `/tmp` 日志方案。
  3. 文档同步（`CODEBUDDY.md`/CORE.md 提及 config.yaml 处、开发日志记一笔）。
- **老系统零改动**（`TEAGE_CONFIG` 机制原样）。
- **回滚**：删除新文件、启动改回默认路径即回滚，**无数据迁移**（实际运行时存储由 `host_components` 的 Rust 代理接管于 `data2/storage_rust/sessions.db`，与配置文件无关）。注意：新文件中的 `storage.sqlite_path` 已由 `data/sessions.db` 改为 `data2/sessions.db`（§6），此项仅在"代理缺位走 SQLite 兜底"时才生效，回滚即随之失效，无残留数据。
- **风险（评估时）**：两文件并存期间 `llm` 段双份维护。→ **实施后状态**：`llm` 段确为双份（这是解耦的代价，也是收益来源）；因两系统已无键值共享，**双份维护不再有"改一处影响两系统"的危险**，仅需在升级 provider/model 时记得两处都改。另：核实老系统 `storage` 段消费的**评估前置项已完成**（见 §1，结论为老系统三键全读）。

**缺陷与修复记录（本次自查发现）**

- **`start_liu2.ps1` 首版编码错误（已修，属本次引入的缺陷）**：仓库既有 4 个 `.ps1` 均为 **UTF-8 BOM + CRLF**，首版脚本却是**无 BOM + LF** → PowerShell 5.1 的 `-File` 对无 BOM 文件按系统 ANSI（GBK）解码，中文注释字节被误解，**行号错位（`--factory` 实际 89 行、报错指向 85 行）**，并抛出 `Missing closing '}'` 与 `Missing expression after unary operator '--'`（`--` 报错只是下游症状，非根因）。修正：转 UTF-8 BOM + CRLF 后 `Parser::ParseFile` 语法检查 **0 错误**，实跑通过。
  - **教训**：① Windows 下新建 `.ps1` 必须与仓库既有脚本同编码（带 BOM），否则中文注释会击穿解析；②**语法检查通过 ≠ 可用**，首版在"看起来写完"的状态下从未被执行，是这次自查（实跑脚本）才暴露的；③ 定位此类问题应比对报错行号与文件实际内容，行号偏移即指向编码/字符集问题。
