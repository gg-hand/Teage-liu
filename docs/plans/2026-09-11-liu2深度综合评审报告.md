## 1. P0（2 项，须优先处理）

### P0-1 跨 session 并发共享 `_mode_instance.final_snapshot` → 跨会话状态串扰（两路子评审独立发现，交叉验证）

- **根因**：`ChatPipeline` 构造时创建单例形态实例（`core/pipeline.py:112`），`ReactLoop.final_snapshot` 是**实例字段**，每个推进点覆写（`core/loop.py:107,118,172,183,275,286,345,360`）；`chat_stream` 开头也重置（`pipeline.py:193`）。
- **触发条件**：`SessionLocks` 按 `session_id` 加锁（`server/session_locks.py:33-60`），**不同 session 真并发**。A 会话在 `await` LLM 期间，B 会话把共享 `final_snapshot` 覆写为 B 的快照；A 收尾时：
  1. `after_all`/`on_error_all` 观测钩子拿到 **B 的终态快照**（`pipeline.py:332-334,363`）→ audit 记录错会话；
  2. `_persist_session_extra(A, final_snapshot)` 把 **B 的 extra 写进 A 的 SessionStore**（`pipeline.py:369-388`）→ 跨会话数据串写，下一轮 A 恢复到 B 的 extra 基座（`pipeline.py:162-167`）。
- **为什么不是设计取舍**：`CORE.md` §6 并发契约声称"core 单快照无共享，并发安全依赖外壳 session 级锁"——该前提**不成立**，`final_snapshot` 正是 core 内跨会话共享的可变对话态。2026-09-09 修"SetStop 陈旧快照"时把它固化成了机制。
- **测试盲区**：现有并发用例只锚定同 session 串行化（`test_server_routes.py:201-241`），**跨 session 并发零覆盖**——正是本缺陷藏身处。
- **建议**：终态快照改为对话级传递（`run_stream` 显式交付 / done 事件携带 / `session_id` 键控 dict 或 contextvar），并补"双 session 并发、extra 互不串写"测试。

### P0-2 行为套件用例 14/15 核心断言不承重（假绿直接污染 P-1/P-2 转档证据）

- **证据**：
  - `cases/14-lifecycle-reload.json:26-28`：`rollback_preserved_old_chain` / `setup_idempotent_reentrant` 期望均为 `{ "type": "boolean" }`；
  - `cases/15-evolution-negotiation.json:44-47`：三态计数均为 `{ "type": "integer" }`、`all_actions_match` 为 `{ "type": "boolean" }`；
  - `runner.py:90-113` `match_value`：`{type:"boolean"}` 对 `False` 同样通过；
  - `runner.py:1161-1162`：negotiation 逐场景 mismatch 只置 `all_match = False` 写入 payload，**从不 append 到 errors**。
- **后果**：把 `negotiate_protocol_version` 三态判定整个删掉（全返回 proceed）或把 `registry.rebuild` 回滚删掉，用例 14/15 **仍绿**。而 PENDING **P-2 条件②、P-1 条件①正以这两例为"满足"证据申报转 `stable`**。同套件其他用例（06/11/12/17/23/24）均用精确字面量，此两例是漏网。
- **建议**：改精确字面量断言（`all_actions_match: true`、三态计数精确值 2/2/3 等），并让 runner 在 negotiation mismatch 时直接 `errors.append`。
