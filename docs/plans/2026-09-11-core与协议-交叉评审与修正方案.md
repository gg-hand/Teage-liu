## 3. P1-1 ~ P1-3 定案

### 3.1 P1-1：`tool_result` 的失败原因表达

**现状**：`loop.py:230` 在 tool_result 上发 `termination_reason="tool_rejected"`。

**协议侧事实**：
- `events.schema.json:72-85` ToolResultEvent 为 `additionalProperties:false`，无该键；
- `events.spec.md:14` 关键字段清单无该键；
- `errors.spec.md:48` 明确：`tool_rejected` 的事件呈现 = **"tool_result is_error 回喂（可能继续至 done）"**；
- 语义错位：`tool_rejected` 是 **done 专用终止原因枚举值**，而 reject 场景对话**继续**（用例 32 自身 `final.termination_reason = normal` 即为铁证）。

**两条路**

| 路 | 内容 | 优点 | 致命问题 |
|---|---|---|---|
| 1 | 只删越界键 | 协议立即自洽 | "策略拒绝"与"执行异常"在事件面**不可区分**（两者 `is_error` 均为 true）→ 第三方观测扩展（audit）拿不到机器可读原因，能力缺口保留 |
| 2 | 删越界键 **+ 在 schema 定义语义正确的可选字段** | 事件面具备机器可读失败原因 | 需走协议演进流程 |

**判据（evolution 域第三阶 RFC：「能否由现有 custom/组合实现」）**
- `custom:*` 第一阶只覆盖 `Event.type` / `Hook.name` / `Action.op`，**不覆盖"给既有事件加字段"**；
- 组合实现：无可用的机器可读信号（`result` 是自由文本，协议不承诺可解析）→ **不能**；
- 故允许按第二阶入 **minor 演进**（新增**可选**字段 = 向后兼容添加，老消费方忽略即可）。

**字段名对比**

| 候选 | 评价 |
|---|---|
| `termination_reason` | **否决**：语义错位（tool_result 不是终止事件），与 done 枚举混用 |
| `rejected: bool` | **否决**：只能表达"是否被拒"，不能表达原因；无法与 `TOOL_EXEC_FAILED` 共存 |
| `code: string`（errors 域码） | **采纳**：复用既有 18 码体系；与 `error` 事件的 `code` 同名同义；可同时承载 `TOOL_REJECTED_BY_POLICY`（拒绝）与 `TOOL_EXEC_FAILED`（执行异常）；直接补齐 P-8 三面模型的①事件面 |

**定案**：**删越界键 + 新增可选 `code`**。
- 发射点：reject → `TOOL_REJECTED_BY_POLICY`；工具执行异常 → `TOOL_EXEC_FAILED`；成功不带。
- 连带收益：`TOOL_EXEC_FAILED` / `TOOL_REJECTED_BY_POLICY` 由"仅日志面"升级为"事件面 + 日志面"，三面模型更完整；用例 32 断言改为 `code`。

### 3.2 P1-2：`step_start.step`

- 语义 = "第几次 LLM 调用"（1-based）；
- 协议侧证据齐整：`events.schema.json:21` `minimum:1`、`StepSummary.round` 亦 `minimum:1`（`:128`）、套件对照侧 `runner.py:1080` 用 `1`；
- 被否决方案：改 schema 允许 0 —— 属**协议迁就实现缺陷**，且与 `round` 口径冲突。

**定案：改代码。** `StepExecutor.execute` 增 `step` 形参（默认 `1`，向后兼容既有调用点），`loop` 传 `cur.round`，`BareMode` 传 `1`；schema 不动。

### 3.3 P1-3：`usage` 口径分裂

- 事实：同一语义（LLM usage）在 **4 处**两种口径——`DoneEvent.usage`（可空）、`AfterResponse.usage`（可空）vs `StepEndEvent.usage`（必填 object）、`StepSummary.usage`（必填 object）；
- 语义：provider 未上报 usage 是**真实且普遍**的场景；`null` = 未上报，`{}` = 上报但为空——用 `{}` 会**丢失语义**，并使 `DoneEvent.usage=null` 退化为几乎不可达的死分支（`loop.py:150` 透传 step_end 的 usage）；
- 被否决方案：改代码发 `{}` —— 语义失真，且是"协议迁就实现"的保守解。

**定案：改协议。** `StepEndEvent.usage` 与 `StepSummary.usage` 放宽为 `["object","null"]`，与同族字段统一；代码不动（`None` 即真实状态）。

## 4. P1-7 定案：热重载 `cancel_all`

**事实链（已复核）**
1. 契约三方均称"热重载重建时 cancel_all 兜底"：`lifecycle.spec.md:10`（L-4）、`transport.spec.md:31`（T-4）、`tasks.py:5-7,69-74`；
2. 实现：`cancel_all` 仅 `registry.py:279`（shutdown）调用；`supervisor.py:216/262` 注释"重建不取消旧链后台任务"；`registry.py:212` 注释称"由 Supervisor 在回滚/成功路径负责"（Supervisor 亦未做）→ **三处注释互相甩锅**；
3. **粒度缺陷**：`TaskRegistry.cancel_all()` 是**全局**的（无链粒度）。热重载时序 = ①spawn 新 → ②新链 setup → ③teardown 旧链 → ④替换；在 ③ 执行全局 cancel_all 会**误杀新链刚注册的任务**；
4. **语义不成立**：对"扩展侧登记任务"，`cancel_all` 只是 `self._registered.clear()`（清登记表），`cancel_task` 只是 `pop` + 改状态——**宿主物理上无法取消扩展进程内的任务**。故 L-4 承诺的"宿主兜底取消旧扩展后台任务"**在语义上无法兑现**。

**liu2 理念判据**：主干最小化 / 扩展自持（`tasks.py:5-6` 自述"任务归属扩展进程，扩展 teardown 自取消"）/ 契约必须可兑现。

| 方向 | 内容 | 判定 |
|---|---|---|
| A | 改代码：`TaskRegistry` 引入 owner 维度 + 热重载按旧链取消 | **否决**：让宿主背上任务生命周期管理（新增契约+复杂度），与"主干最小、扩展自持"相悖；且对扩展侧任务依旧无效 |
| B | 修正契约：明确"扩展侧任务由扩展 teardown 自取消（宿主仅登记/可观测）；宿主侧任务由 **shutdown** 全局兜底；**热重载不做全局 cancel_all**" | **采纳**：契约可兑现、与理念一致、零代码行为变更 |

**定案：方向 B。** 改 `lifecycle.spec.md` L-4、`transport.spec.md` T-4、`core/tasks.py` docstring、`core/registry.py:212` 注释；`docs/INTERFACES.md:302` 已是正确表述，不动。
