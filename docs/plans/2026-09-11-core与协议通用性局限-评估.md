# core 与协议 通用性局限 评估

> 日期：2026-09-11。状态：评估完成（只读分析，未改任何代码）。
> 定位：**不针对任何具体扩展**。本文只回答一个问题——当扩展形态从"观测/干预类"走向"主动/服务类"（调度、工作流、批处理、多智能体 worker）时，当前 core 与 PROTOCOL 有哪些**结构性**局限。
> 关联：`docs/plans/2026-09-11-workflow作为扩展-评估.md`（workflow 是本次暴露局限的载体，但不是结论的对象）、`docs/plans/2026-09-10-协议收口与遗留债-解决计划.md`（存量协议债）、`teage_liu2/PROTOCOL/evolution/evolution.spec.md`（第一阶演进通道）。
> 用户观点（2026-09-11）："core 和协议的升级不服务于任何扩展，但每次升级都能兼容更多可能。"

## 0. 结论摘要

发现四类局限，按"是否需要新增能力面"排序：

| 类别 | 性质 | 数量 | 处置成本 |
|---|---|---|---|
| **A 契约信用**：协议/文档承诺过、实现未兑现 | **最伤（扩展无法从契约推断真实行为）** | 4 项 | 低（多数是补齐或撤回，不需新协议面） |
| **B 方向性不对称**：扩展永远是被动方 | 架构定位问题（钩子模型的必然结果） | 1 项（含 4 条表现） | 高（需先定调，再新增通用主动通道） |
| **C 正交能力缺口**：任何规模稍大的扩展都会撞上 | 基础设施/能力面残缺 | 7 项 | 中（逐项独立，可分批） |
| **D 隔离的合法代价**：有意设计带来的边界 | 不是缺陷，但要知道边界在哪 | 2 项 | 不修（只在文档写明） |

**核心判断**：当前最急的不是"缺能力"，而是 **A 类契约信用**——协议预留了演进面（`custom:*`）、manifest 声明了授权面（capabilities）、规范写了任务语义（T-4）、文档写了生命周期兜底（cancel_all），但四处都没完全兑现。扩展作者必须逐行读 core 才能知道"哪些承诺是真的"，这是平台化最大的障碍，而且**修复它们不需要新增任何协议元素**。

## 1. 评估视角与准入判据

一个升级提案是否值得进 core/协议（即"不服务于任何扩展，但兼容更多可能"的可操作化）：

1. **与扩展名无关**——core 不知道任何枝干名（依赖铁律）；
2. **正交能力补齐**——不是某扩展的专用通道；
3. **现有扩展零改动受益或零影响**——向后兼容；
4. **可写成通用条款并被行为套件覆盖**——可测试、可回归。

四条全中 → 进 core/协议；缺任一 → 留在扩展侧。本文 §6 的分层按此判据给出。

反例（说明判据有效）：为 workflow 单独新增"反向 `invoke_tool`"（扩展请求宿主派发链上工具）满足 1/2，但破坏 3/4（扩大所有扩展的安全面、难以写成通用套件条款），故不采纳——这是判据的实际应用。

## 2. A 类：契约信用（承诺未兑现）

### A-1 `custom:*` 第一阶演进通道在 core 零实现（最严重）

**协议承诺**（`PROTOCOL/evolution/evolution.spec.md:16-19`）：

```
第一阶: 自定义扩展点（不改协议即可用）
  Event.type → "custom:*"   # core 透传, 观测扩展可消费
  Hook.name  → "custom:*"   # 扩展声明实现, core 通用触发点调用
  Action.op  → "custom:*"   # 扩展间传递, core 记录+忽略
```

**行为条款 V-1**（同文件 `:31`）："core 对未知 type/op/hook 的策略 = 透传/记录，**绝不崩溃**。"

**实现事实**：

- core 全目录 grep `custom` —— **0 命中**（`teage_liu2/core/` 无任何 custom 处理）；
- `make_action` 对未知 op **抛 `ValueError`**（`core/actions.py:108-110`），`ACTION_CLASSES` 与 `validate_action` 只认 6 类（`:119-159`）；
- `RemoteBranchAdapter._actions_from` 捕获异常后 **log error + 跳过**（`core/remote_adapter.py:120-123`）；
- `HookChain` 是 11 个硬编码钩子方法，**没有"通用触发点"**可被 `custom:*` 挂载；
- 事件流由宿主产生（`event_stream` / pipeline），**扩展无上行事件的通道**。

**后果**：三个面全部悬空——Action 被静默丢弃（仅日志）、自定义钩子无处注册、自定义事件无产者。协议"不改协议即可扩展"的第一阶能力在实现层不存在。这是"兼容更多可能"目前**只是纸面**的直接证据。

**处置（二选一，不能悬空）**：①补齐实现（让 V-1 成真：未知 op 记录并透传、未知 hook 名有通用派发、事件上行通道）；②从协议撤回第一阶（改 `evolution.spec.md`，承认三阶演进中第一阶未落地）。

### A-2 manifest 的"授权面"语义只兑现了 1/4

- 声明面：manifest `capabilities` 是唯一事实源，且校验"代码声明 ⊆ manifest 授权面"（`core/extension_loader.py:221-228`）；值域 = `observe / tool_executor / llm / self_hosted_storage`（`core/hooks.py:37-40`）。
- 实现面：**只有 `llm` 被真校验**——`_handle_invoke_llm` 首段检查 `CAP_LLM`（`core/transport.py:557-564`）。其余：
  - `storage_*` 只校验 kind 前缀（`:601-607`），**不校验 capability**；
  - `task_register` / `task_cancel` 无任何 capability 校验（`:658-684`）；
  - `tool_executor` / `observe` 只是"派发通道选择 / L3 订阅"的开关（`hooks.py:359-375`、`app.py:77-92`）；
  - `self_hosted_storage` 纯声明，无代码校验。

**结论**：协议里的 capability 更像"声明标签"而非"运行期授权"。任何扩展都能读写自己前缀的存储、登记任务，与授权声明无关。

### A-3 `task_register` 语义空洞（两层）

- **语义层**：`TaskRegistry.register_task` 只写内存字典，**不承载执行**（`core/tasks.py:45-51`）；`cancel_task` 只标记 `status="cancelled"`（`:53-59`）。T-4 的"宿主登记/可观测/协调取消"里，只有"可观测"部分有一张表。
- **实现层**：`InProcessHostPort.register_task` / `cancel_task` 是**同步方法**却调用 async 的 `self._bus.handle(...)` 且**未 await**（`core/transport.py:754-763`）→ 协程被丢弃，`task_register`/`task_cancel` 消息**永不执行**（并产生 `RuntimeWarning`）。同文件 `storage_*` / `invoke_llm` 均为正确 async。

**处置**：①把任务做实（宿主托管：扩展注册协程 → 宿主 `create_task` → shutdown/热重载统一取消）；或②明确降级为"纯可观测登记"并写进契约；无论选哪个，`await` 缺陷必须修（推荐改 `async def` + `await`）。

### A-4 文档与代码漂移

| 文档表述 | 代码事实 | 位置 |
|---|---|---|
| `INTERFACES.md:302`："宿主 shutdown 与**热重载重建**时 cancel_all 兜底" | `registry.rebuild` **不调用** `cancel_all`（注释 `:212` 明示"不取消旧链后台任务"），`cancel_all` 全仓仅由 `registry.shutdown` 调用 | `core/registry.py:167-218`、`:278-279` |
| `INTERFACES.md:297-298`：扩展在 teardown 自取消 | 与代码一致（这条是对的） | — |

**处置**：文档跟随代码（写明"热重载不 cancel，扩展必须自清理"），或按契约修代码（属 core 行为变更，需评估"回滚保旧链"语义）。

## 3. B 类：方向性不对称（扩展永远是被动方）

**消息方向清单**（`core/transport.py:43-61` + `TransportBus.handle:508-549`）：

| 方向 | 消息 | 语义 |
|---|---|---|
| 宿主 → 扩展 | `invoke_hook` / `invoke_tool` / `event` / `shutdown` | 调用扩展、投递观测、关闭 |
| 扩展 → 宿主 | `invoke_llm` / `storage_write` / `storage_read` / `storage_query` / `storage_delete` / `task_register` / `task_cancel` / `heartbeat` | **全部是"资源访问"** |

**缺口**：扩展→宿主方向**没有任何一条"请求某件事发生"的通道**：

- 不能请求宿主"跑一次完整对话"（复用工具/护栏/记忆/落盘）；
- 不能请求宿主"派发一次链上工具调用"；
- 不能向另一个扩展投递消息（前向也禁止，见 D 类）；
- 不能向主对话事件流上行事件。

**性质**：这是钩子模型（宿主驱动、扩展响应）的必然结果——对观测/干预类扩展（audit、guardrails）完美，对**主动/服务类扩展**（调度、工作流、批处理、多智能体 worker）是天花板。

**待定调的架构问题**：liu2 是"宿主驱动的扩展平台"，还是"可自持的扩展平台"？若是后者，需要新增的是**通用主动通道**（子会话 / 中介投递 / 事件上行），而不是为某个扩展开小门。这个问题比任何单个扩展的取舍更重要。

## 4. C 类：正交能力缺口（与扩展名无关）

| # | 缺口 | 证据 | 撞上它的扩展类型 |
|---|---|---|---|
| C-1 | 扩展加载**无包语义**：loader 用 `spec_from_file_location` 且明示"不污染 sys.path"；现存扩展全为单文件 `main.py` | `core/extension_loader.py:186-210`、`:192` | 任何 >1 文件的扩展 |
| C-2 | `invoke_llm` **能力面窄**：无 `tools` / `tool_choice` / 流式 / 超时 | `core/transport.py:239-257`、`:736-752` | 任何自实现 agent 循环的扩展 |
| C-3 | `storage_*` **只有增删查**：无 `update`（读-改-写非原子）、`query` 仅顶层字段精确匹配（无范围/排序）、无 `count` | `core/transport.py:601-653`、`core/storage.py:167-191` | 任何维护状态机的扩展 |
| C-4 | manifest **无 config schema**：扩展配置靠各扩展手写 `setup` 校验 | `core/extension_loader.py:30-34`（无 config 字段）| 所有带配置的扩展 |
| C-5 | 装配语义硬编码：顺序 = config dict 顺序（无 `order`/`requires`）；任一 `setup` 失败 = **全局启动失败**（无 `degrade`） | `core/registry.py:114-128`、`:223-249` | 可选增强型扩展（与项目"降级优先"风格相悖） |
| C-6 | **无扩展状态只读暴露**：installed/enabled/degraded/health 只存在于日志与内存 | `supervisor._degraded` 未暴露；`/reload` 仅返回名字列表（`server/routes.py:200-206`） | 运维、前端、用户 |
| C-7 | 版本协商**只管协议 major/minor**，不协商能力集 | `core/transport.py:125-161` | 需按 core 能力降级的扩展 |

## 5. D 类：隔离的合法代价（有意设计，写清边界即可）

- **D-1 无扩展间调用 / 无跨扩展读**：由 kind 前缀隔离（`core/transport.py:300-315`）+ 无相关消息类型保证；`storage.spec.md:32`（S-3）明文"跨扩展数据查询当前禁止"。代价：**多智能体协作在 liu2 里没有物理通道**（要协作只能靠宿主中介，而宿主目前没有中介能力——`event` 是唯一近似形态且只下行）。这直接决定了"调度与引擎必须同扩展"（见 workflow 评估）。
- **D-2 同语言扩展与宿主同进程、无资源配额**：只有钩子超时（`hook_timeout`）与 `invoke_llm` 信号量（4）。重扩展应被引导用 stdio（通道已有），但缺"何时该用"的判据。

## 6. 分层升级建议

### 第 0 层：先修"契约信用"（不加任何能力面，成本最低、通用性最高）

1. `custom:*` **二选一**：补齐实现（V-1 成真）或从协议撤回（§2 A-1）；
2. **capability 授权矩阵**：兑现 manifest 授权面（`storage_*` / `task_*` 也应校验 capability），这是所有扩展的安全基线（§2 A-2）；
3. `register_task` **兑现或降级** + 修 `await` 缺陷（§2 A-3）；
4. **文档-代码漂移清理**（§2 A-4）。

### 第 1 层：正交能力补齐（逐项独立）

5. 扩展**包语义**（C-1）；
6. `invoke_llm` 对齐 `chat_role` 公共能力（C-2）；
7. `storage` 原子 `update`（乐观并发）+ `query` 增强 + `count`（C-3）;
8. manifest 声明 **config schema**，宿主统一校验（C-4）；
9. `degrade` 失败策略 + 显式 `order`/`requires`（C-5，需先裁决"扩展是否允许声明依赖"）；
10. 扩展**状态只读暴露**（C-6）+ 能力集协商（C-7）。

### 第 2 层：架构性（需先定调）

11. **扩展主动通道**（子会话 / 中介投递 / 事件上行）——前提是 §3 的定位问题有答案（B 类）；
12. **任务托管**（宿主执行扩展任务，T-4 做实）；
13. **扩展级 reload**（当前只有全局链级 `/reload`）。

### 不做

- 扩展间直连（破坏隔离，D-1）；
- 为单一扩展开专用消息（违反准入判据 2）；
- 把调度/工作流等业务语义搬进 core（违反依赖铁律）。

### 7.1 处置登记（2026-09-11，用户裁决方向）

- **`custom:*` 第一阶演进通道 → 后续执行（走立项评估路线）**。不在本次直接做"补齐实现 / 撤回协议"二选一，而是先立**「`custom:*` 落地」立项评估**（内容应含：三类 custom 的语义与作用域、core 的透传与记录点、与 `remote_adapter` 跳过路径的关系、V-1 条款如何被行为套件覆盖、是否升 VERSION、对 `actions.py` 未知 op 抛错语义的调整）。立项评估产出后才谈执行计划。**本次不做。**
- **capability 授权矩阵 → 不能本次直接完成，需独立立项**。核查判定（4 条）：
  1. `Capability` 枚举是 **v1.0.0 协议冻结面**（`PROTOCOL/lifecycle/lifecycle.schema.json:16-20`，仅 `observe` / `tool_executor` / `llm` / `self_hosted_storage`）——把 `storage_*` / `task_*` 纳入授权校验**必须新增能力值**，属协议变更，须先写 `PENDING.md` 走 proposed→experimental→stable→merged 并裁决版本策略。
  2. **授权矩阵语义未定义**（设计决策，非补齐）：哪个通道 ↔ 哪个 capability；`self_hosted_storage` 与宿主 `storage_*` 是否互斥；扩展未声明时的默认语义（**默认拒绝**会破坏兼容、**默认允许+告警**则授权面形同虚设）。评估原文只写了"storage_*/task_* 也应校验 capability"，未给矩阵。
  3. **破坏现有扩展（准入判据③"现有扩展零影响"不满足）**：`data2/extensions/audit/manifest.yaml` = `capabilities: [observe]`，但其代码经 `host_port.storage_write` 落盘 `kind=audit.*`；`guardrails` / `storage_rust` 均为 `capabilities: []`。一旦对 `storage_*` 强制校验，**audit 立即被拒** → 需迁移方案与兼容窗口。
  4. **性质冲突**：M1 的立身之本是"零新裁决依赖"，塞入授权矩阵会把 M1 一并变成待裁决项。
