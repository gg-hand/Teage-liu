## 1. 三个待裁决

### 1.1 WP-E 步骤 0：CI 依赖（`fastapi` + `httpx`）

**事实复核**

- CI 装机行只装 4 包：`python -m pip install pytest pyyaml jsonschema python-dotenv`（`.github/workflows/liu2-audit.yml:48`），且**不安装** `pyproject.toml` 依赖。
- `teage_liu2/server/routes.py:9-10` **模块级** `from fastapi import APIRouter, Request` + `from fastapi.responses import JSONResponse, StreamingResponse`。
- `teage_liu2/server/app.py:16-18` **模块级** `from fastapi import FastAPI` 等。
- `fastapi` / `httpx` 均已在 `requirements.txt:4,10` 与 `teage_liu2/pyproject.toml:7,13` 声明。
- 当前 `tests_core/` **无任何 fastapi import**（唯一提及是 `test_server_stdio_proxy.py` 声明"本文件不依赖 fastapi/httpx"）。
- **先例**：`python-dotenv` 之所以进入 CI 最小集，正因 `core/config.py:25` 模块级硬依赖（workflow 头注释明示）；而 `core/llm.py:11` 把 anthropic/openai **延迟到 backend 构造**，故 CI 不需要它们 —— 即 CI 最小集的既定原则 = "覆盖被测试代码的**模块级 import 全集**"。

**方案复核（对原三方案的关键更正）**

| 方案 | 原描述 | 复核结论 |
|---|---|---|
| **A** | workflow 追加 `fastapi httpx` | **成立**。1 行改动；与"覆盖模块级 import 全集"原则一致（fastapi 是 `server/` 的模块级 import），与 `python-dotenv` 先例同理；CI 略慢（fastapi 传递依赖 starlette/pydantic 等，非重依赖） |
| **B** | server 测试拆 `tests_server/`，CI 与 `audit_liu2.ps1` 都不跑 | 成立但**代价高**：routes 是最贴近生产的模块（4 个生产修复在此），CI **零覆盖**；本地/CI 门禁不一致，易漏跑 |
| **C** | 不经 FastAPI，直接调路由函数 + 构造 `starlette.requests.Request` stub | **不成立（事实更正）**：`routes.py` 自身模块级 import fastapi，**只要 import 它就仍需 fastapi**。C 只能省掉 `httpx`、**不能省掉 fastapi**，**仍须改 workflow**，却失去真实装配面 → 被 A 严格支配 |
| **D**（补充） | `pytest.importorskip("fastapi")` | 可让 CI 变绿，但**以"静默跳过"换绿**：`-q` 下跳过不显眼，routes 仍无 CI 门禁，且会掩盖 fastapi 真装坏的情况 → 不建议作主方案 |

**受影响任务**（均需 import `server/routes.py` 或 `server/app.py`）

- WP-E·E1：routes 4 个生产修复锚定（拦截取 `done.response`、`/reload` 序列化 500、`before_id` 分页 …）；
- WP-E·E4：L-11 routes 级并发；
- 其余 E2/E3（`host_components` / `stdio-proxy`）**不依赖 fastapi**，已落地。

**推荐**：**方案 A**。附带更新 workflow 头注释，写明 `fastapi`/`httpx` 进入最小集的理由（与 `python-dotenv` 同款：被测试模块**模块级 import**），使"最小依赖集"原则保持自洽。
**成本**：1 行 + 注释；CI 安装 fastapi 及传递依赖，耗时增加有限。
**风险**：无（本地已装，行为不变）。唯一约束 = 改 workflow 属配置改动，须批准。

### 1.2 L-11 的 routes 级端到端真并发

**契约原文**（`PROTOCOL/lifecycle/lifecycle.spec.md:17`）："同 session_id 的并发对话**由外壳串行化**（会话级互斥是外壳责任，非 core 能力）……若外壳未串行化，extra 恢复/写回表现为 last-writer-wins 或丢失更新（语义未定义）。"

**现状**

- 机制：`server/session_locks.py`；接线：`server/routes.py:44-45`（`/chat`）、`:87-88`（`/chat/stream`，锁在 `event_source` 内、覆盖整个 SSE 流）。
- 已锚定：`tests_core/test_session_locks.py`（同 session 串行 / 不同 session 独立 / LRU 淘汰 / 持有不淘汰 / `drop`·`clear`）。
- **未锚定**：routes **真的获取并持有**该锁 —— 若删掉 `routes.py` 的 `get` + `async with`，现有测试仍全绿。

**新发现（附带但重要）：`SessionLocks` 边界语义漏洞**

- 文档承诺（`session_locks.py:9-11,36-38`）：超限时淘汰空闲锁，"仅当全部锁同时持有/等待时才允许缓存临时超限"。
- 实际代码（`:45-54`）：超限时扫描首个**未持有**的锁淘汰。但**刚创建、尚未被调用方 `async with` 的那把锁本身就是"未持有"**，因此在"其余锁全被持有"时会被自己淘汰 —— 即"允许临时超限"的 `break` 分支**不可达**。
- 后果：`get(sid)` 在满缓存场景可能返回一把**未被登记**的锁；随后同一 `sid` 再 `get` 会创建**另一把** → **同 session 拿到两把不同锁，互斥失效**（正是 L-11 要防的"丢失更新"）。
- **证据**：现有测试 `tests_core/test_session_locks.py:65-76`（`test_held_lock_not_evicted`）已把这行为当"契约"编码 —— `max_size=1`、持有 `s1` 后 `get("s2")`，断言 `_locks` 只剩 `s1`、`size==1`，即 **`s2` 刚发出就被淘汰**。
- **生产影响**：默认 `max_size=10000`，需 1 万个**同时持有**的会话才触发，实际风险极低；但这是与文档承诺相悖的**真实语义缺陷**，足以让"L-11 已覆盖"的登记站不住脚。

**端到端测试设计要点（若采纳）**

- **`TestClient` 必须用上下文管理器**（`with TestClient(app) as c:`）：这样所有请求共享同一 portal/event loop；否则每个请求各自 loop，而 `SessionLocks` 的 `asyncio.Lock` 在请求处理器内**惰性创建**，跨 loop 复用会抛 `RuntimeError`。
- **确定性优先**：不要在用例里 `sleep` 赌时序；用 `asyncio.Event` / `threading.Event` 让第一个请求"进入并阻塞"，再断言第二个请求尚未进入 pipeline，最后放行。
- 三种粒度（可组合）：

  1. **单元级**（已有）：`SessionLocks` 机制；
  2. **路由协程级**（推荐新增）：`await chat(request, body)` 两次 `asyncio.gather`，`request.app.state` 注入真 `SessionLocks` + 假 pipeline（barrier 控制）→ 确定性验证"routes 真持锁串行"，**只需 fastapi、不需 httpx**；
  3. **`TestClient` 端到端**（可选）：真 HTTP 栈 + 线程并发；覆盖最全但最易 flaky，且需 `httpx`。

- **建议**：以 ② 为主锚（覆盖接线、确定性好），③ 作冒烟（若采纳方案 A 可顺带做）。
- **同时**：补一条**边界单元用例**（满缓存 + 同 session 两次 `get` → 必须同一把锁），该用例在当前实现下**必红**，正好锁住上述漏洞；修复方向 = 淘汰时跳过"本次刚创建/刚返回"的锁（或按文档语义允许临时超限）。

**阻塞**：任何 import `server/routes.py` 的测试都需要 fastapi → 依赖 1.1 的裁决。

### 1.3 T-3 是否强制只读

**条款拆解**（`PROTOCOL/types/types.spec.md:47`）：T-3 含两半 ——（a）"快照对扩展呈现为**不可变只读视图**"；（b）"扩展**不得修改**快照本身，只能通过返回 Action 变更"。

**现状**

- `Snapshot` 是 `@dataclass(frozen=True)`（`core/types.py:349`），但 `messages` / `tools` / `extra` / `history` 是**可变容器**（`:362-366`）→ 冻结只锁**属性赋值**；扩展原地 `snapshot.messages.append(...)` 会成功并污染 core（`CORE-缺口记录.md` H-17，P2 未修）。
- 内核侧不变量**已锚定**：`test_snapshot_identity.py`（属性赋值被拒 / 推进返回新实例且原实例不变 / 元素对象同一 / 禁 deepcopy）。
- 套件 `cases/31-hooks-readonly` **如实锚定"篡改生效"**（缺口修复后须收紧为 `[user]`）。

**信任域分析（关键）**

- **异语言 / stdio 扩展**：快照经 wire 序列化下发、action 经 wire 回传 → 扩展拿到的是**副本**，原地改写不回传，**天然只读**；H-17 与它们无关。
- **同进程扩展**：与 core 同进程同权限，可 `import` core 任意模块直接改状态；对其强制"快照只读"**无安全增益**，只有**防误用**价值。

**选项对比**

| 选项 | 做法 | 成本 / 风险 |
|---|---|---|
| **S1** 不强制（现状 + 措辞） | 保持契约；修订 T-3 措辞区分信任域（跨进程强制 / 同进程约定） | 最低；诚实；扩展误改仍会污染 |
| **S2** 边界只读视图 | 仅在调用同进程钩子时，把交给扩展的快照包一层只读视图（`messages`→`tuple`、`extra`→`MappingProxyType`），core 内部仍用 list | 中：改 `hooks.py` 调用点；扩展若做 `snapshot.messages + [...]` 会因 `tuple + list` 报错（契约可见变化）；每次钩子 O(n) 转换 |
| **S3** 全局不可变容器 | `Snapshot` 直接存 `tuple` / `MappingProxyType` | 高：`types.py` / `snapshot.py` / `assembler.py` / `loop.py` 大面积改（`messages + [x]`、`List[Message]` 注解、`_SizeCache` 同一性检查）；与 §18.2 零拷贝 / T-5 目标摩擦 |
| **S4** 检测式 | 交出发前记指纹、收回后比对 | 不可靠：篡改已污染同一对象，无法回滚（除非先拷贝，违 T-5） |

**推荐**：**S1** —— 不把 T-3 当安全能力承诺，仅作契约 + 防误用说明。理由：H-17 的实际价值是**防误用**而非安全；S2/S3 收益与成本不成比例，S3 还与已冻结的性能契约（§18.2 / T-5）冲突。
**若确需防误用**：退选 **S2**（边界只读视图），并同步把 `cases/31` 收紧为 `[user]`；验收锚 = `cases/31` 收紧 + 新增"原地篡改被拒"单测。

## 3. LLM_CANCELED 的锚定方式

**事实复核**

- `core/step.py:113-121`：`StreamCancelled` → `logger.info("%s: LLM 流被用户取消", LLM_CANCELED)` + `error` 事件 `code=LLM_CANCELED`。
- `PROTOCOL/errors/errors.spec.md:66`：**LLM_CANCELED 属 ①「事件面」**（`error.code`）；`:67` 的 ②日志面清单**不含** LLM_*。
- 单测已锚**事件面**：`tests_core/test_step_error_codes.py::test_llm_canceled_code`。
- 套件未锚：`cases/20-error-codes.json` 的 `must_include` 无 `LLM_CANCELED`（其 description 明写"info 级不入 warning+ 捕获，由单测覆盖"）。
- PENDING P-8 条件②口径是"套件对拍覆盖 **≥ 12 码**"，现套件并集**恰 12 码**（未含 LLM_CANCELED）→ **条件②已按其字面满足**；LLM_CANCELED 属**硬化项**、非达标必需。

**新发现：`error-codes-20` 的"事件面"通道实际为空**

- `runner.py:1142-1147`：协议层用例的错误码断言同时取"事件面"（`_extract_codes(json.dumps(custom_events))`）与"日志面"（`capture.records`）。
- 但 `_run_error_code_matrix(case)`（`runner.py:1342`）**不接收也不写入 `custom_events`**（该列表是 `_run_protocol_case` 的局部变量，`runner.py:921`）→ **case 20 的事件面永远为空**。
- 于是 case 20 里 LLM_* 全部**只靠日志面侥幸通过**（LLM_TIMEOUT / STREAM_FAILED / API_ERROR 恰好用 warning / error 记日志）；**规范指定的事件面（面①）在套件中形同虚设** —— 这是一处潜在**假绿**（删掉 `error` 事件的 `code` 键，case 20 仍可能绿）。

**三种做法**

| 做法 | 内容 | 评价 |
|---|---|---|
| ① 改 core 日志级别 | `step.py` 的 `logger.info` → `warning` | **不建议**：用户取消是正常动作（`errors.spec.md:44` 明示 user_cancel **非错误**），warning 语义错；且等于**发明**一条规范未要求的日志面义务 |
| ② runner 下调包 logger 级别 | 捕获期间 `logging.getLogger("teage_liu2").setLevel(DEBUG)`，用完还原 | 可行、仅测试工具改动；但仍是去锚"规范未要求的面"，且依赖日志级别这一实现细节 |
| **③ runner 转发事件面**（推荐） | `_drive` 收集 `error` 事件的 `code`，经 `custom_events` 暴露（如 `custom:error_matrix.payload.event_codes`），用例 20 的 `must_include` 加 `LLM_CANCELED` | **规范正确**（锚面①）、**零 core 改动**、顺带修好"case 20 事件面为空"的潜在假绿；套件错误码并集 **12 → 13** |

**推荐 ③**；可选叠加 ②（若还想锚日志面）。**不推荐 ①**。
**注**：当前"套件 + 单测 **18/18 全码**"结论不变；③ 只是把 LLM_CANCELED 从"仅单测"提升为"套件事件面 + 单测"，并消除 case 20 事件面空转。
