# 配置校验严格性 — 立项评估

> 触发：`docs/plans/2026-09-17-两系统配置解耦-立项评估.md` §2 风险 6（"非 `core` 段无未知键校验 → typo 静默失效"）需根治，故启动本评估。
> 性质：**只评估，不改代码、不改配置、不升 VERSION**。评估结论与修订方案供裁决。
> 关联契约：`teage_liu2/PROTOCOL/config/config.spec.md`（v1.0.0）、行为套件 `cases/21-config-domain.json`、`cases/24-host-component-reject.json`。

## 0. 结论速览

1. **"严格校验限 `core` 段"这一设计是合理的**，且**有契约依据**（`config.spec.md` §1 明文 + 行为条款 **C-1**）与**套件锚定**（case 21 显式固化该边界）。其合理性来自依赖铁律：core 不知道任何枝干名，**无法**校验扩展段键名 —— 根级 `additionalProperties: true` 是必然，不是妥协。**此边界应保留。**
2. **但"合理的原则"落地不完整，存在 3 个具体缺口**（其中 1 个是**契约违规**）：
   - **G1（契约违规，严重）**：`host_components[].backend` 键名拼错 → **静默回落内置 SQLite**，直接违反 `config.spec.md` §3 的三处明文（backend "必填"∈注册表 / "未注册 = 启动失败" / "**不做静默降级、不回落内置实现**"）。
   - **G2（覆盖空洞）**：C-1 只定义两类归属（core 段↔core、扩展段↔扩展）。`llm` / `storage` 段**既非 core 段、也非扩展段**，却由 core 与外壳直接消费 → 协议未指派归属，实现零校验。
   - **G3（委派未达目标）**：C-1 把扩展段校验委派给扩展 setup，但现网扩展只做**值校验**、未做**未知键拒绝** → 该机制宣称的目的（防 typo 静默失效）未达成，最严重后果为**安全枝干静默关停**。
3. **建议**：G1 立即修（零迁移成本）；G2 与"取消 `config.yaml` 回落"合并立项（否则会打断默认启动路径，见 §6）；G3 由 core 提供校验助手 + SPI 纪律并施。

## 1. 契约怎么说（现状事实）

| 条款 | 原文要点 | 出处 |
|---|---|---|
| 校验范围 | "严格校验——未知键拒绝、类型/范围校验，失败 = 启动失败（可读错误列未知键）。**严格校验限 core 段**（根级 `additionalProperties: true`：扩展段键名由扩展声明面决定，根级放行，2026-09-11 注明）" | `config.spec.md` §1 |
| **C-1 配置段归属** | "core 段由 core 校验，**扩展段由扩展在 setup 自校验**（收到自己的配置段）" | `config.spec.md` §1 行为条款 |
| C-2 敏感字段 | `${VAR}` 占位 + `.env` 分离 + 脱敏为既有功能资产 | 同上 |
| host_components | "`slot`: 必填,∈ SLOTS 白名单"；"`backend`: **必填**,∈ BACKENDS 注册表"；"未注册 = 启动失败"；"**失败语义**：上述任一非法配置一律 = **启动失败（可读错误）**，不做静默降级、不回落内置实现" | `config.spec.md` §3 |
| 演进规则 | 新增 core 配置键 = minor；删除/改名配置键 = major；扩展配置段由扩展自管 schema | `config.spec.md` §4 |

## 2. 实现现状（三层校验矩阵）

| 层 | 消费方 | 校验位置 | 类型/范围 | 未知键拒绝 | 判定 |
|---|---|---|---|---|---|
| `core` 段 | core | `core_config_from` | ✅ | ✅（白名单，列未知键） | **完整** |
| 扩展段 `core.branches.<name>` | 各扩展 | 扩展 `setup()` 自校验 | ✅（部分） | ❌ | **缺未知键拒绝** |
| `llm` 段 | core（`LLMClient` / `get_llm_timeouts`） | 无专门校验 | ❌ | ❌ | **零校验** |
| `storage` 段 | 外壳（`app.py`）+ `host_components._sqlite_backend` | 无专门校验 | ❌ | ❌ | **零校验** |
| `host_components` | 外壳（`load_host_components`） | slot/backend 白名单 + options 类型 | 部分 | ❌ | **部分严格，且有静默回落** |

补充事实：
- 扩展 setup 的**值校验确实已实现**（C-1 已落地）——`guardrails.setup` 校验 `denylist` 为字符串列表、`action ∈ {block, warn}`；`audit.setup` 校验 `record_steps` 为 bool。
- 分支配置的传递路径：生产装配走 `BranchRegistry.setup_all` —— `core/registry.py:230-242` 逐枝干传 **`branch_cfg`（该枝干自己的配置段）**，`server/app.py:298` 调用的正是它；分支自身段的来源是 `registry.build` 经 `loader(name, branch_cfg)`（构造时）。
  → **C-1 括注"（收到自己的配置段）"在生产路径是正确的**（本项曾于本文件早前版本误判为"与实现不符"，已在 2026-09-18 执行前审查中纠正；误判源于把 `core/hooks.py:256-261` 的 `HookChain.setup_all`（传全局 cfg、**仅测试使用**）当成了生产路径）。
- **附带观察（不在本次范围）**：`HookChain.setup_all(config, host)` 与 `BranchRegistry.setup_all(config, host_builder)` **同名但配置语义相反**（全局 cfg vs per-branch 段）—— 同名不同义是审计误判的温床，建议后续在 `hooks.py` 该方法 docstring 显式标注"非生产装配路径"。

## 3. 实证：typo 后果分级（本轮实测）

| # | 拼错位置 | 实测后果 | 级别 |
|---|---|---|---|
| **A** | `host_components[].backend` → `backand` | **未报错**，装配对象回落为 `SQLiteStorageProvider` / `SQLiteHistoryStore` —— Rust 存储后端整体不装配，实际存储路径由 `data2/storage_rust/sessions.db` **静默变为** `data2/sessions.db` | **严重（契约违规）** |
| B | `host_components[].slot` → `slott` | 启动失败 ✅（白名单拦截），但错误信息为"未知插槽 None"，**未提示拼错的键名** | 安全（信息不友好） |
| C | entry 内多余键（如 `optons`） | 静默忽略 | 中 |
| **D** | `core.branches.guardrails.denylist` → `denylst` | **未报错**，`denylist = []`，且 `setup` 的值校验**放行**（`[]` 是合法列表）→ **拦截能力静默关停** | **严重（安全相关）** |
| **E** | `llm.main_base_urll` | **未报错**，`main_base_url = None` → 静默回落 provider 默认端点（可能把请求发往非预期端点） | **严重** |
| F | `llm.actvity_timeout` / `storage.sqlite_pth` | **未报错**，回落默认（60 / `data2/sessions.db`） | 中 |

**套件覆盖盲区**：`cases/24-host-component-reject.json` 已测"**值**非法"（`backend: "nope"` → "未知 backend"），但**未测"键缺失/键名拼错"**（`backend` 缺席 → 取默认 `sqlite`）。这正是 A 场景的向量 —— 套件有"未知 backend"断言却漏掉最易发生的 typo 形态，属**假绿式覆盖**，与项目"根除假绿"纪律冲突。

## 4. 判定：配置校验是否合理？

**分为两个问题，答案不同：**

**Q1「core 段严格校验」是否合理？→ 合理且必要，应保留。**
- 契约（`config.spec.md` §1、C-1）+ 套件（case 21）双重锚定，意图明确（"防 typo 静默失效，老系统踩过的坑"）。
- 实现完整（类型 + 范围 + 未知键 + 白名单 + 错误码）。

**Q2「严格校验**限** core 段」这一边界是否合理？→ 原则合理，但当前落地有 3 个缺口（G1/G2/G3），不完整。**
- **合理之处**：core 不知道枝干名（依赖铁律），**不可能**枚举扩展段键名，故根级必须放行 —— 这是设计必然。
- **G1 不合理（契约违规）**：`backend` 静默回落内置实现，与 §3 三处明文冲突。**这是"实现没做到契约已声明的事"，不是"要不要加严"的取舍问题** —— 无需权衡，应修。
- **G2 不合理（覆盖空洞）**：C-1 的二分法（core 段 / 扩展段）**遗漏了 `llm` / `storage` 这类"宿主段"**。它们由 core 与外壳消费、键集由 liu2 自持，**归属本应唯一且明确**，却无人校验。属契约设计疏漏。
- **G3 不合理（委派未达目标）**：C-1 的委派机制本身成立，但"委派"不等于"达标" —— 未要求扩展做未知键拒绝，实际就只做到值校验。**D 场景（安全枝干静默关停）表明该缺口的后果与 spec §1 宣称的目的直接背离**。

## 5. 修订方案（分级）

| 编号 | 内容 | 性质 | 迁移成本 |
|---|---|---|---|
| **R1**（建议立即实施） | `host_components[].backend` 由"有默认值 `sqlite`"改为**必填**：缺失或未注册一律启动失败（与 `slot` 对称）；同时修正 B 场景错误信息，提示"`slot` 缺失或键名拼错" | **实现补契约**，非新增严格性 | **零**（现网 `config.yaml` 与 `config-liu2.yaml` 均显式写了 `backend`） |
| **R2**（建议与 R5 合并立项） | 为 `llm` / `storage` 段补未知键拒绝（键集由 liu2 自持，可枚举：`llm` 11 键 / `storage` 1 键） | 校验语义收紧 + 补 C-1 归属 | 见 §6（**前置依赖 R5**） |
| **R3**（建议并施） | 扩展段 typo 防护：core **无法**校验扩展段键名（铁律），故 (a) **SPI 纪律**：要求扩展 setup 做自身段未知键拒绝；+ (b) **core 提供校验助手**（如 `reject_unknown_keys(segment, allowed, code)`）供扩展主动调用 —— core 只提供工具、不感知枝干名，**不违铁律** | 纪律 + 机制 | 低（现网 guardrails/audit 段键名均已合规） |
| **R4**（随 R1/R2） | 协议文本同步：`config.spec.md` §1 的 C-1 表述修正（"构造时收到自己的配置段"）+ 归属扩展为三类（core 段 / 宿主段 `llm`·`storage` / 扩展段）；按 §4 属"校验语义收紧"，需在 `PENDING.md` 登记（涉及域含 config） | 文档/协议登记 | — |
| **R5**（独立立项，R2 的前置） | **取消 liu2 对 `config.yaml` 的回落**，默认/强制读 `config-liu2.yaml` | 行为变更 | 见 §6 |

## 6. 迁移风险（R2 的前置依赖，务必先看）

**关键事实**：老系统的 `config.yaml` 之 `llm` 段含 `context_threshold`（**liu2 不消费**）。而 liu2 当前在**未设 `TEAGE2_CONFIG`** 时回落读 `config.yaml`。
→ **若 R2 直接对 `llm` 段做未知键拒绝，该回落路径会立刻启动失败**（`context_threshold` 成为"未知键"）。

三条出路：

| 方案 | 内容 | 评价 |
|---|---|---|
| (a) 容忍键白名单 | 把 `context_threshold` 列入 liu2 的 `llm` 段"容忍但不用"白名单 | 与本次键级清理（剔除死键）**相悖**，重新引入"配置里有不消费的键"这一温床 |
| **(b) 取消 `config.yaml` 回落（R5）** | liu2 默认/强制读 `config-liu2.yaml` | **推荐**："回落读老系统配置"正是本次解耦要消灭的隐患类别（`storage.sqlite_path` 指向老系统库即由此而来）。移除后 R2 方可安全落地，且与"两系统彻底解耦"定则一致。属行为变更，须单独立项 |
| (c) 未知键仅告警 | 记警告但不失败 | 违背项目"失败 = 启动失败、不静默降级"文化，**不建议** |

**R3 的兼容性检查**：现网 `config-liu2.yaml` 的 `core.branches.guardrails`（`enabled` / `denylist` / `action`）与 `audit`（`enabled` / `record_steps`）键名均已合规 → 加白名单后**无迁移风险**。
