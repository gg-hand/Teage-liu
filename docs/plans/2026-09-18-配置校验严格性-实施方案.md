### 1.2 原子任务

**任务 1.2.1 — 实现对齐 schema（`teage_liu2/server/host_components.py`）**

在 `load_host_components` 的 entry 循环内，按以下**顺序**校验（顺序经审查确认：entry 类型校验须最前，其后新增检查不得让既有 `match=` 用例失去原意图）：

1. **未知键拒绝** → `CONFIG_UNKNOWN_KEY`：entry 键集 ⊆ `frozenset({"slot", "backend", "options"})`，列出未知键
2. **必填检查** → `CONFIG_MISSING_KEY`：`slot` / `backend` 缺失即失败；错误信息**须提示"缺失或键名拼错"**并列出该 slot 的可用 backend
3. **slot 白名单** → `CONFIG_INVALID_VALUE`（原文案"未知插槽"保留，供套件 `expect_regex` 匹配）
4. **backend 注册表** → `CONFIG_INVALID_VALUE`（原文案"未知 backend"保留）—— **删除 `entry.get("backend", "sqlite")` 默认值**
5. 其余既有分支（重复接管 / options 非映射 / 返回映射校验 / ABC）文案不变，仅**统一补 `CODE: ` 前缀**

**错误码前缀**（对齐 `errors.spec.md:69` ④ 面；**复用既有三码，不新增码** → 不触发 R-2 新增码流程）：
`撤销 v1 的"先不补码"建议` —— 审查认定不补码即属漂移。既有失败分支一并补前缀，使 ④ 面"覆盖码"声明成真。

**G4 一致性修正**：改为区分"缺席/`None` = 缺省"与"其他非数组 = 失败"：

```python
raw_entries = cfg.get("host_components", None)   # 注意:不用 `or []`
if raw_entries is None:
    return {}
if not isinstance(raw_entries, list):
    raise ValueError(f"{CONFIG_INVALID_VALUE}: host_components 必须是数组,"
                     f"实际 {type(raw_entries).__name__}")
entries = raw_entries
```

**示意代码修正**（v1 有 bug，照抄会抛 `TypeError` 而非 `ValueError`）：
```python
_ENTRY_ALLOWED_KEYS = frozenset({"slot", "backend", "options"})

unknown = sorted(set(entry) - _ENTRY_ALLOWED_KEYS)
if unknown:
    raise ValueError(f"{CONFIG_UNKNOWN_KEY}: host_components[{i}] 含未知键: "
                     f"{', '.join(unknown)}(可用: {', '.join(sorted(_ENTRY_ALLOWED_KEYS))})")

missing = [k for k in ("slot", "backend") if k not in entry]
if missing:
    slot_hint = entry.get("slot")
    avail = sorted(BACKENDS.get(slot_hint, {}))      # ← 必须查 BACKENDS（值为 backend 注册表）
    raise ValueError(f"{CONFIG_MISSING_KEY}: host_components[{i}] 缺少必填键: "
                     f"{', '.join(missing)}(键名拼错也会落到此;"
                     f"slot={slot_hint!r} 可用 backend: {avail})")
```
> ⚠ **不得**写成 `sorted(SLOTS.get(...))` —— `SLOTS` 的值是 **ABC 类元组**，`sorted` 会抛 `TypeError`（v1 示意代码即为该错）。

## Phase 2：取消 `config.yaml` 回落（R5）— 需单独裁决

- 现状优先级：`config` 参数 > `config_path` 参数 > `TEAGE2_CONFIG` > **默认 `config.yaml`**。
- 动机：**"回落读老系统配置"正是解耦要消灭的隐患类别**（`storage.sqlite_path` 指向老系统库即由此而来）。
- 建议形态：默认改为 `config-liu2.yaml`；缺失即**启动失败（可读错误）**，不再静默回落。
- 同步面：`INTERFACES.md:347` 示例、`core/config.py` 的 `load_config` 默认值注解、`CODEBUDDY.md`、`start_liu2.ps1`；并核查 `tests_core` 是否有依赖默认路径的用例。

## Phase 3：`llm` / `storage` 段校验（R2）— 依赖 Phase 2

- **契约前置**：schema 中 `llm`/`storage` 目前仅 `{"type":"object"}`（无属性定义）→ 直接加 `additionalProperties:false` 会禁止所有键；须**先补齐键集定义**（`llm` 11 键 / `storage` 1 键 + 类型/范围）。
- **归属补全**：`config.spec.md` §1 的二分法须扩为三类：core 段 / **宿主段 `llm`·`storage`** / 扩展段。
- **迁移风险（关键）**：老系统 `config.yaml` 的 `llm` 段含 `context_threshold`（liu2 不消费）；Phase 2 未先行则"回落 + 严格校验" = **立即启动失败** → 这就是 Phase 2 必须在前的原因。
- 演进分类须在 `config.spec.md` §4 明确；套件新增 `cases/47-config-host-segment-strict.json`。

## Phase 4：扩展段 typo 防护（R3）

- core **不能**枚举扩展段键名（铁律）→ 两路并施：(a) **SPI 纪律**（写入 `lifecycle.spec` / `SUBSYSTEM-SPI.md` §12 接入三步法 / `INTERFACES.md` 模板）；(b) **core 提供校验助手**（`reject_unknown_keys(segment, allowed, segment_name)`）供扩展主动调用 —— core 只提供工具、不感知枝干名，不违铁律。
- 验收：`guardrails`/`audit` 改用助手 → 用例证明"扩展段 typo → 启动失败"（当前 G3 场景 D 为**静默关停**）。
