## 0. 结论摘要

| 项 | 裁决 |
|---|---|
| **立项** | **建议立项**。workflow = `kind: branch` 的 `language: python` 扩展，落 `data2/extensions/workflow/`，经 extensions_root 目录发现 + `core.branches.workflow` 启用 |
| **装载方式** | 目录发现（生产唯一通道）。**不使用** `register_factory` —— 其定位被代码明文限定为"测试/行为套件/编程式嵌入注入通道，非生产装载方式"（`core/registry.py:53-64`、`server/app.py:200-202`） |
| **调度** | 扩展**自持**：`setup` 内 asyncio tick（60s）+ 自研 5 字段 cron 解析（纯标准库）；调度状态持久化到 `workflow.schedules` |
| **执行** | step 类型收敛为 3 类：`llm`（经 `host_port.invoke_llm`）/ `tool`（扩展自带插件目录）/ `agent`（扩展内 mini ReAct）；**舍弃** `deterministic`（老模板遗留）与 `subworkflow`（老系统本就是 stub） |
| **管理面** | 声明 `capabilities: [llm, tool_executor]`，管理经**主对话工具集**（`workflow_create/list/get/update/delete/run/runs/confirm`）——零外壳改动、零新增路由、天然进入 `pre_tool_call` 链 |
| **工具步骤** | 扩展**自带插件目录**（形态沿用老系统 `cron_tool/<name>/run.py` + `TOOL.md`），**子进程**执行（隔离崩溃 + 可超时 kill + 语言无关） |
| **持久化** | 全走 `host_port.storage_*`，kind 前缀 `workflow.`（`workflow.schedules` / `workflow.runs` / `workflow.state`）；**不写主对话历史**（不污染会话） |
| **协议改动** | **零**（不新增消息/钩子/schema）。建议仅登记 PENDING 观察条目 P-9 + 修复 2 项宿主缺陷（§8） |
| **明确不做** | host-component 形态 / core 内置调度 / 拆双扩展 / 反向 `invoke_tool` 通道 / 邮件通知 / 老系统 setattr 注入 |

**分期**：M1 最小可用（装载 + 调度 + `llm` step + 工具面最小集）→ M2 完整（`tool` step + 失败策略 + 运行记录查询 + catch-up）→ M3 增强（`agent` step + 只读观测页 + 通知可选）。

## 1. 动机与主张

### 1.1 老系统的接入方式是"注入"，这正是主张要避免的

`teage_liu/tasks/scheduler.py:1311-1394` 构建 `WorkflowContext` 时，用 `setattr` 把 `tool_registry / cron_tool_registry / policy_engine / audit_logger / skill_loader / session_logger / react_loop / run_id / orchestrator / session_id` 动态挂到 context 上（`_INJECT_COMPONENTS` 见 `scheduler.py:269-275`，`_collect_components` 见 `scheduler.py:1293-1309`）。这些字段**多数不在 dataclass 声明中**（`base.py:86-163` 只声明 10 个字段），后果是：

- 依赖隐式：谁需要什么只在运行期才知道，IDE/静态检查无能为力；
- 不可单测：测试一个 step 执行器要构造整个 orchestrator 及其组件；
- 逆向依赖：`WorkflowContext` 里塞进了 orchestrator 引用（业务对象持有编排器）。

### 1.2 liu2 的等价能力已存在，且是协议化的

liu2 的扩展经 `host_port`（`InProcessHostPort`，消息语义）访问宿主能力，**不以对象引用访问宿主对象**（`core/transport.py:691-697` 明文）。这意味着同一份能力在两种形态下语义一致：

- 同语言（python）：`host_port.storage_write(...)` → `TransportBus.handle` 消息路径；
- 异语言（stdio）：同一条消息经帧传输。

依赖变成**显式 + 可 mock + 可跨语言**，这是主张成立的技术基础。

### 1.3 为什么不并入"协议收口与遗留债"计划

`docs/plans/2026-09-10-协议收口与遗留债-解决计划.md` 是**协议面**收口（P-1..P-8 入协议条件 + 20 条条款覆盖 + 测试锚定），其验收是"套件 21→39 条、PENDING 条件勾稽"；workflow 是**新功能面**，两者验收口径不重叠。把它塞进那份计划会同时污染"协议冻结面"与"新功能范围"。故本评估独立成文，落地时另立执行计划。

## 3. 约束面：liu2 能给什么（代码事实）

### 3.1 扩展可获得的能力：`host_port` 7 方法

| 方法 | 位置 | 语义 | workflow 用途 |
|---|---|---|---|
| `storage_write(kind, docs)` → doc_ids | `transport.py:703-709` | 经 `MSG_STORAGE_WRITE`；宿主侧**走 StorageWriter FIFO 队列**（`:618-621`） | 存定义/运行记录 |
| `storage_read(kind, doc_id)` | `:711-717` | 经 `asyncio.to_thread` 直读 | 读单条 |
| `storage_query(kind, limit=None, **filters)` | `:719-727` | filters = doc 顶层字段**精确匹配**（`storage.py:167-191`） | 列定义/查运行记录 |
| `storage_delete(kind, doc_id)` | `:729-734` | — | 删定义 |
| `invoke_llm(role, messages, system, max_tokens)` | `:736-752` | 直调 `LLMClient.chat_role`；**强制 `llm` capability**（`:557-564`）；信号量 4（`:474`） | `llm` / `agent` step |
| `register_task(task_id, description)` | `:754-758` | 宿主登记（可观测） | 登记调度循环（**注意 §8.1 缺陷**） |
| `cancel_task(task_id)` | `:760-763` | 协调取消 | teardown |

异语言扩展经 12 消息类型（`transport.py:43-61`）访问同一批能力；扩展→宿主方向两边等价（`handle` 分支 `:508-549`）。

### 3.2 硬约束（逐条给证据）

1. **扩展不能注册 HTTP 路由 / 不能暴露端点**：路由静态定义（`server/routes.py` 全文 6 个端点：`/chat`、`/chat/stream`、`/sessions/{id}/messages`、`/reload`、`/health`、`/`），无动态 `add_api_route`，扩展与 server 层无接口。
2. **无"扩展管理/查询"入口**：全仓无"列扩展/查扩展状态"端点；最接近的是 `/reload` 返回 `branches` 名列表（`routes.py:200-206`）。
3. **无扩展间调用通道**：12 消息类型无"调用别的扩展"项；`invoke_tool` 是**宿主→扩展**方向（`remote_adapter.py:211-226`、`hooks.py:359-375`），扩展入站 `invoke_tool` 落 `unknown_message_type`（`transport.py:538-543`）。
4. **无"扩展请求宿主执行链上工具"的通道**：扩展→宿主仅 `invoke_llm / storage_* / task_* / heartbeat`（`transport.py:528-537`）。
5. **storage kind 前缀隔离，跨扩展读写被拒**：`check_kind_prefix`（`transport.py:300-315`）；`storage.spec.md:32`（S-3）明文"跨扩展数据查询走 RFC，当前禁止"。
6. **无 cron / 周期任务基础设施**：穷举 `cron/schedule/interval/sleep` 仅命中心跳（`stdio.py:385-430`，30s）、L3 窗口（`event_stream.py:247`，50ms）、退避（`llm.py:149/175`、`supervisor.py:323`）——**无任何可复用的通用调度**。
7. **扩展任务需自清理**：`TaskRegistry.create_task` 才真正被 `cancel_all` 取消（`tasks.py:35-40`）；`register_task` 只是登记（`:45-51`）。**热重载 `registry.rebuild` 不调用 `cancel_all`**（`registry.py:167-218`，注释 `:212` 明示"不取消旧链后台任务"）；`cancel_all` 全仓仅由 `registry.shutdown` 调用（`registry.py:278-279`）。故扩展必须在 `teardown` 自取消并 await 收尾。
8. **`invoke_llm` 不支持 `tools` 参数**：`validate_payload_schema`（`transport.py:239-257`）与 `InProcessHostPort.invoke_llm`（`:736-752`）均无 `tools`，尽管底层 `chat_role` 支持。→ `agent` step 的工具 schema 只能以**文本**形式进 prompt，由扩展自行解析工具调用意图（或扩展自行定义轻量协议）。
9. **`invoke_llm` 无超时**：宿主侧无超时参数，扩展须自包 `asyncio.wait_for`；并发受宿主信号量 4 约束。
10. **"禁止在 before/inject_round 调 invoke_llm"仅是文档约定**（`INTERFACES.md:332`），无代码强制；workflow 的调用发生在**后台任务**，不在钩子内，不受该约定限制。
11. **扩展代码 capability ⊆ manifest 授权面**（`extension_loader.py:221-228`）；manifest 严格白名单字段（`:30-34`），未知键 = 拒绝。
12. **多文件 python 扩展的子模块导入无先例**：`load_python_extension` 用 `spec_from_file_location` + `exec_module`（`extension_loader.py:194-210`），docstring 明示"**本装载器不污染 sys.path**"（`:192`）；现存扩展（`data2/extensions/{audit,guardrails,storage_rust}`）**全部是单文件 `main.py`**，无自举先例。→ workflow 是多文件扩展，**入口自举方案必须先验证**（§9 风险 R1）。

### 3.3 三个真实缺口（本评估要裁决的）

| 缺口 | 性质 | 处置（§6.5） |
|---|---|---|
| G1 工具能力：workflow 无法使用链上其他扩展的工具 | 架构性（隔离设计使然） | **自带插件目录**（D1） |
| G2 触发入口与管理界面：扩展无路由、无管理端点 | 外壳能力缺失 | **工具面**（D2） |
| G3 长任务/跨重启：宿主 cancel 语义 + 热重载不 cancel | 生命周期语义 | 扩展自持久化 + 自清理（D4） |

## 4. 方案空间与对比

| 方案 | 形态 | core/外壳改动 | 能力上限 | 结论 |
|---|---|---|---|---|
| **A 单 branch 扩展（自持调度+引擎+自带工具）** | `data2/extensions/workflow/`，`capabilities:[llm, tool_executor]` | **0**（+§8.1 三行修复） | LLM 全能力 + 自带工具；无 UI | **推荐（M1/M2）** |
| A+ `invoke_chat`（扩展请求宿主跑一次完整对话） | 同 A + 新增协议消息 | core 协议面 + host_port + TransportBus | 复用链上工具/护栏/审计/记忆 | **不推荐为主路径**（见 D1）；可登记观察 |
| A+ 反向 `invoke_tool`（扩展请求宿主派发单个工具） | 同 A + 新增协议消息 | core 协议面 + 安全面 | 复用链上工具（需自跑多轮） | **不推荐**：安全面（任意扩展可调任意工具）> 收益 |
| B 拆两个扩展（scheduler + engine） | branch × 2 | 0 | — | **不可行**：枝干互不可见 + storage 前缀隔离（约束 5），后台无对话上下文故 `extra` 通道也不可用 |
| C host-component 形态 | `language: other` + `slots` | 需新增 SLOTS/BACKENDS | 只能**接管宿主插槽对象**，不能承载行为 | **排除**：manifest 强校验 `kind: host-component` 必须 `language:other` + 非空 `slots` + `capabilities == []`（`extension_loader.py:126-131`），且语义是"接管插槽"（`host_components.py:28-32`），workflow 是行为不是插槽对象 |
| D core 内置调度 | `core/` | 违反依赖铁律 | — | **排除**（用户已定调"归入扩展管理"） |
| E 外壳内置调度（`server/` 持有 tick，扩展提供引擎） | 外壳 + 扩展 | 外壳感知"workflow"语义 | 外壳要 import/编排扩展名 | **排除**：违反"外壳只依赖 core、不感知任何枝干名"（`CODEBUDDY.md` 铁律 + `app.py:37-42` 明文） |

**排除论证要点**：方案 B 常被当作"解耦"直觉选项，但 liu2 的隔离设计使其**在物理上不可行**——`storage_query` 的 kind 必须带自身前缀（约束 5），`snapshot.extra` 只在对话上下文存在而调度是后台路径，`custom:*` 扩展间 Action 在实现层被 `make_action` 拒绝并跳过（`remote_adapter.py:113-124`）。因此**调度与引擎必须是同一个扩展**。

## 5. 老系统与推荐方案的能力对照（"更好"在哪）

| 维度 | 老系统 | liu2 推荐方案 | 改进来源 |
|---|---|---|---|
| 依赖获取 | `setattr` 动态注入（`scheduler.py:1311-1394`），多数字段未声明 | `host_port` 显式方法（消息语义） | 可静态检查、可 mock、可跨语言 |
| 可测性 | 需构造完整 orchestrator | 扩展可注入 fake host_port；测试放 `tests_branches/`（仓库纯净例外已授权） | 单测成为可能 |
| 管理入口 | 专有前端 + `/schedules`、`/proposals`、`/cron_tools` 三类路由（~1143 行） | 主对话工具集（自然语言管理） | 零路由、零前端、天然过 `pre_tool_call` 链 |
| 审批状态 | 内存（`cron_proposals.py:9-10`，重启即丢） | `workflow.state` 持久化两阶段 | 不丢 |
| 失败计数 | 内存（`scheduler.py:335`） | 持久化 | 重启后可继续计数/禁用 |
| 定义与运行记录 | YAML 文件 + JSONL 目录 | 统一 storage kind | 与扩展存储模型一致；可被外壳观测 |
| 重载 | 改代码需重启服务 | `POST /reload` 即可换扩展（`routes.py:143-206`） | 开发迭代快 |
| step 类型 | 5 类（含 2 类废/stub） | 3 类（去死代码） | 面积收敛 |
| 与主对话关系 | 独立调度路径，绕过 CronIsolator（且 react step 不走工具白名单，`research.py:182-200` 为 no-op） | 管理动作走主对话工具调用，受同一套钩子/策略约束 | 语义统一 |
| 主对话污染 | 运行写独立 session | **不写主对话历史**（只写 `workflow.*`） | 会话列表干净 |

**诚实的代价**（不掩饰）：

1. **工具生态隔离**：workflow 无法调用链上其他扩展（如天气扩展）的工具——由自带插件目录补偿，但生态是分裂的；若将来需要融合，须走 §12 裁决项 R-1（新增协议消息）。
2. **无 UI（M1/M2）**：管理靠对话；可视化编排需 M3 的外壳通用观测端点（另立项）。
3. **扩展是宿主进程内的 python 代码**：长任务必须全 async（禁同步 IO 阻塞事件循环）；工具插件用**子进程**隔离（§6.6）。

### 6.4 调度循环与生命周期

```python
class WorkflowBranch(Branch):
    name = "workflow"
    capabilities = ["llm", "tool_executor"]

    async def setup(self, config: dict, host: Any) -> None:
        # ① 配置自校验（失败 = 启动失败，不静默）
        # ② 从 storage 恢复 schedules / state（重启恢复，约束 7）
        # ③ 起 tick 任务 + 登记
        self._task = asyncio.create_task(self._tick_loop())
        if self.host_port is not None:
            self.host_port.register_task("workflow.tick", description="调度 tick")  # 见 §8.1

    async def _tick_loop(self) -> None:
        try:
            while True:
                await asyncio.sleep(self._tick_seconds)
                now = datetime.now()
                if self._minute_key(now) == self._last_minute:
                    continue
                self._last_minute = self._minute_key(now)
                for sched in self._schedules.values():
                    if sched.enabled and cron_matches(sched.cron, now):
                        await self._run(sched)          # 串行（老系统语义一致）
        except asyncio.CancelledError:
            raise

    async def teardown(self) -> None:
        # 幂等可重入：取消 tick + await 收尾；在途 run 标记 interrupted
        ...
```

- **tick 粒度与去重**：60s + `%Y-%m-%d %H:%M` 去重（对齐 `scheduler.py:443-458`）；
- **串行语义**：单 tick 内逐 schedule await（对齐老系统）；跨 schedule 的并发上限由 `max_concurrent_runs` 控制（建议 M2 再加信号量）；
- **catch-up**：setup 恢复后检查 `next_run < now`，按 `catch_up_policy` 处理（`skip` = 直接顺延；`execute_once` = 补跑一次）；
- **重启恢复**：`next_run` 由 cron 现算，不依赖进程内存；未完成 run（`status=running` 且无 `finished_at`）在 setup 时标记 `interrupted`——**不自动续跑**（避免副作用重放）；
- **teardown 义务**：扩展自取消（热重载不 cancel，约束 7），并在 `teardown` 内冲刷待写（`host_port.storage_write` 本身已 await 完成）。

### 6.5 执行引擎

```
engine.run(spec, ctx):
  ① 校验 spec（step id 唯一 / depends_on 存在 / 无环 / type 合法）
  ② 拓扑排序（DFS 三色，环 → 报错退出）
  ③ 逐 step：workflow 级 timeout 检查 → condition 求值（不满足 = skipped）
       → 执行（executor 按 type 分派）→ step_outputs[id] = outputs
       → 失败策略：fallback（换 executor 跑 fallback_config）/ skip / abort
  ④ 汇总 step_traces → 写 workflow.runs
  ⑤ 失败：连续失败计数 +1（持久化）；达阈值 → enabled=false
```

| step type | 输入 | 实现 | 输出 |
|---|---|---|---|
| `llm` | `config.prompt`（可引用 `depends_on` 的上游 outputs） | `await host_port.invoke_llm(role="main", messages=[...], system=...)`，外层 `asyncio.wait_for(step_timeout)` | `{"response": "<拼接的文本块>"}` |
| `tool` | `config.tool` + `config.input`（模板变量替换） | 插件子进程（§6.6） | `{"result": ..., "tool": ...}` |
| `agent` | `config.prompt` + `config.tools[]` | 扩展内 mini ReAct：`invoke_llm` → 解析工具意图（文本协议）→ 插件执行 → 回喂，最多 `max_rounds` 轮 | `{"response": ..., "tool_calls": [...]}` |

- **上游引用**：`depends_on` 的上游 outputs 以 `[前置步骤 {id} 输出]\n{...}` 形式前置进 prompt（对齐 `step_executor.py:314-348`）；
- **工具 schema 传递**：受约束 8，`invoke_llm` 无 `tools` 参数 → `agent` step 的工具说明以**文本**注入 prompt，工具调用意图由扩展按轻量约定解析（如要求 LLM 输出 ```tool_call {"name":..., "input":...}``` 代码块）；这是与老系统（原生 tool_use）的**能力降级点**，需在 README 明示；
- **超时**：宿主 `invoke_llm` 无超时 → 每个 step 外层 `asyncio.wait_for`（`step_timeout_seconds`）；
- **不可重试判定**：沿用老系统 `NON_RETRYABLE_ERRORS` 思路（工具不存在/参数错/校验错），命中直接 abort。

### 6.6 工具插件（D1 推荐路径）

- **目录形态**：`tools/<name>/run.py`（stdin 收 JSON，stdout 返回 JSON）+ `TOOL.md`（描述 + 参数 schema）——沿用老系统 `cron_tool/<name>/` 约定（`cron_tool/README.md:19-20`、`blog_monitor_joyehuang/run.py`）；
- **执行方式**：`asyncio.create_subprocess_exec(sys.executable, run_py, ...)`，JSON in / JSON out，stdout/stderr 强制 UTF-8（老系统教训：Windows GBK 会让中文崩溃，与 P-4 条款⑦同源）；
- **隔离收益**：插件崩溃不伤宿主进程；超时可 kill；插件可用**任意语言**（sh/node/rust 编译产物皆可），与"扩展语言无关"的架构气质一致；
- **白名单**：schedule 创建时把 `tools` 快照进定义（对齐老系统 `active_tools_snapshot`），运行期只允许定义内工具（防定义被 LLM 顺手改宽）；
- **失败语义**：非零退出 / 非法 JSON / 超时 → 归为 step 失败，进失败策略。

### 6.7 管理面（`tool_executor`）

### 6.8 安全与资源边界

| 面 | 措施 |
|---|---|
| 越权访问 | kind 前缀由宿主强制（约束 5），扩展无法读 `audit.*`/`guardrails.*`/主对话历史 |

| 阻塞事件循环 | 全链路 async；插件隔离在子进程；禁止同步 IO 于扩展主路径（`CODEBUDDY.md` 代码风格约定） |

## 7. 关键决策点（逐条给推荐）

### D1 工具能力路径 —— **推荐：自带插件目录（方案 A）**

| 选项 | 收益 | 代价 | 裁决 |
|---|---|---|---|
| ① 自带插件目录（子进程） | 零协议改动；语言无关；崩溃隔离 | 无法复用链上其他扩展的工具 | **推荐（M1/M2）** |
| ② 反向 `invoke_tool`（新增协议消息） | 复用链上工具 | 新增协议面；**任意扩展可调任意工具** = 安全面显著扩大；仍要自跑多轮 | 不推荐 |
| ③ `invoke_chat`（扩展请求宿主跑完整对话） | 复用工具/护栏/审计/记忆，能力上限最高 | 新增协议面；嵌套对话语义复杂（护栏会拦 workflow 输入？审计混淆？会话命名？防环）；当前 P-1..P-8 尚未 merged，再增协议债 | **M3 再评估**（若确需，登记 PENDING 走 RFC：`evolution.spec.md` 的"现有元素能否组合"红线需正面回答） |

### D2 管理入口 —— **推荐：主对话工具集（M1/M2）+ 通用观测端点（M3，另立项）**

- 专有 `/workflow/*` 路由**排除**：外壳会感知枝干名与语义，违反"外壳只依赖 core"（`app.py:37-42`）；
- 通用端点（如 `GET /extensions`、`GET /extensions/{name}/state`）**不违反**铁律（通用、无枝干名硬编码），但属**外壳新能力**，且要定义"扩展如何声明可观测数据"——建议 M3 单独立项，本评估只登记方向。

### D3 插件执行形态 —— **推荐：子进程**

进程内 `import` 更简单，但插件是 LLM/用户可写的代码，崩溃与阻塞风险由宿主承担；子进程以 ~1 次 spawn 的成本换隔离 + 可超时 + 语言无关。参照：宿主自己的 stdio 扩展也是子进程（`supervisor`）。

### D4 重启恢复与 catch-up —— **推荐：不续跑 + 两策略 catch-up**

- 未完成 run → `interrupted`（不重放副作用，因为 step 可能已产生外部效果）；
- `next_run` 现算；错过的窗口按 `skip`（默认）/`execute_once`。

### D5 通知 —— **推荐：M3 且只用 `urllib`/`asyncio.to_thread` 或不做**

老系统用 `aiohttp`（`notify_hook.py:91`）+ `aiosmtplib`（`:103`）；liu2 依赖清单无此二者，引入它们等于给一个扩展加两个第三方依赖。M3 建议：Webhook 用标准库 `urllib.request` 包 `to_thread`；邮件**不做**。

### D6 是否新增协议消息 —— **推荐：不新增**

本方案在现有协议面（12 消息 + 3 Action 族 + 11 钩子）内闭合，符合 `PENDING.md` 的准入红线（"能否由现有元素组合实现"）。唯一想新增的 `invoke_chat` 属 D1③，M3 再评估。

## 8. 宿主侧前置项（必须先处理）

### 8.1 `InProcessHostPort.register_task/cancel_task` 未 await（真实缺陷）

```python
# core/transport.py:754-763（现状）
def register_task(self, task_id: str, description: str = "") -> None:
    self._bus.handle(                       # ← handle 是 async，未 await
        self._name,
        TransportFrame(MSG_TASK_REGISTER, {...}),
    )
```

`TransportBus.handle` 是 `async def`（`transport.py:508`），不 await 只会创建协程对象并丢弃 → **`task_register`/`task_cancel` 消息永远不会被处理**，并产生 `RuntimeWarning: coroutine ... was never awaited`。同文件其余方法（`storage_*`/`invoke_llm`）都是 `async def` 且正确 await。

- 影响面：仅"扩展任务登记（可观测）"功能形同虚设；扩展自身的 `asyncio.create_task` 不受影响；
- 修法（二选一）：①把两方法改为 `async def` + `await`（调用方 `setup` 是 async，兼容）；②保持同步签名，内部 `asyncio.get_running_loop().create_task(self._bus.handle(...))`（不推荐，异常被吞）。**推荐 ①**；
- 归属：可并入协议收口计划的 WP-E（server/transport 测试锚定）或单列小修。

### 8.2 热重载不取消扩展任务（口径澄清，非缺陷但要写清）

`registry.rebuild` 与 `supervisor.reload` 均**不**调用 `cancel_all`（`registry.py:167-218`、注释 `:171-173`；`supervisor.py:196`），而 `INTERFACES.md:302` 的表述是"宿主 shutdown 与热重载重建时 cancel_all 兜底"——**文档与代码不一致**。

- 对 workflow 的含义：**扩展必须在 `teardown` 自取消 tick 任务**，别指望宿主兜底；
- 建议顺手修文档（`cleanup` 项），或按代码补 `cancel_all`（属 core 行为变更，需单独评估——注意回滚路径上取消新链任务可能破坏"回滚保旧链"语义）。

### 8.3 无扩展管理/观测端点（能力缺口，非缺陷）

M1/M2 不阻塞；M3 观测页的前置（D2）。

## 11. 明确不做

- **不用 `register_factory`**（测试/嵌入通道，非生产装载）；
- **不用 host-component 形态**（语义不匹配 + manifest 强校验）；
- **不在 core / 外壳内置调度**（依赖铁律 + 用户定调）；
- **不把调度与引擎拆成两个扩展**（隔离设计使其不可行）；
- **不新增协议消息**（M1/M2；`invoke_chat` 留待 M3 RFC）；
- **不搬老系统的 `WorkflowTemplate`/`deterministic`/`subworkflow`/`RetryBudget`**（遗留 / stub / 死代码）；
- **不搬邮件通知**（依赖成本）；
- **不做 LLM 自写插件代码并自动激活**（`cron_tool_writer` 式 HIL 硬约束保留）；
- **不写主对话历史**（运行记录独立）；
- **不改 `config.yaml` 等常驻配置**（本评估只出结论；启用时的配置改动须用户批准）。
